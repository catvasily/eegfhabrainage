	- NOTE: It is not straightforward to include existing README.md into the documentation

	- To document an existing code tree:
		. One needs to add the code location to the sphinx system path. This is done by adding commands to
		  config.py file:
			import pathlib
			import sys

			# Assume that the root of the python code is one level up from this file location
			sys.path.insert(0, pathlib.Path(__file__).parents[1].joinpath('preprocessing').resolve().as_posix())
		  If always targeting Linux, one can just use a string as a path specification, without
		  invoking pathlib.Path class:
			sys.path.insert(0, 'your-path')
		  NOTE: it seems that inserting a path this way does NOT insert its SUBFOLDERS

		. One needs a) to create an additional .rst file; b) add this .rst file to index.rst.
		  Inside the new .rst file should be a title (required; this
		  title appears in the table of contents), then autosummary directive, then list of 
		  source files to extract the code from. Example file 'code.rst'
			Code
			====


			This is a simple text at the start of the *code.rst* file. Everything below
			comes from the autosummary directive.

			.. autosummary::
			   :toctree: generated	# 'generated' is the name of a folder where generated
						# sphinx sources for each object are created

   			   qq			# Here the source files (without .py) are listed

		  NOTE that sphinx only recognizes comments properly if the go after the corresponding
		  code element. For example a block """   """ which comes before the function declaration
		  is not parsed and returns an error (~not enough values to unpack).

		  IMPORTANTLY, autosummary only generates a listing  with a single line of per each object - 
		  unless it is customized using templates. Thus function description will only include signature
		  and may be couple of words from the description that come first.

		. Alternative is not to use autosummary, but add directives to the index.rst manually.
		  Useful example:

		  Package qq description
		  -------------------------
		  .. automodule:: qq
		     :members:

		  NOTE: if :members: should be always present, one can add it to autodoc_default_options
		  dictionary in conf.py:
			autodoc_default_options = {
			    'members': True             # This adds :members: option to automodule, autoclass by default
			}

		. IMPORTANT: when generating docs, all modules are IMPORTED by sphinx - including the main
		  scripts. Importing such a script automatically executes it, unless protected with
			if __name__ == '__main__':
		  clause. Thus, to avoid running main program when generating documentation - protect the code
		  with such if statement.

		. Turns out that sphinx does not automatically find packages within a virtual environment.
		  Needed to add path to those explicitly:
		  sys.path.insert(0, pathlib.Path(__file__).parents[1].joinpath('mne/lib64/python3.8/site-packages')\
			.resolve().as_posix())

		. To support .md files as sources (see https://www.sphinx-doc.org/en/master/usage/markdown.html):
			Install MyST-Parser:
				pip install --upgrade myst-parser
			Add 'myst_parser' to the extentions listed in extensions list

		. To avoid each function to be prepended with the module name use
			add_module_names = False
		  in config.py

		. The .rst syntax of class/function description is heavy. Same effect is achieved with using
		  google-style descriptions (used by Nikolay) or Numpy style descriptions (used by MNE). Both
		  are supported using 'napoleon' extention: 'sphinx.ext.napoleon'
			https://www.sphinx-doc.org/en/master/usage/extensions/napoleon.html#module-sphinx.ext.napoleon

		. When using google docstrings, sphinx generates warning about duplicate descripions if Methods: clause
		  is used in the class docstring with short methods definitions, and also detailed definitions are
		  provided in methods definitions. The generated HTML then contains duplicate descriptions of the same
		  function - a short one (from the class/Methods:) and a long one (from the method itself)
		  To avoid it - one can use :noindex: parameter for this module; but then functions from the module do
		  not end up in the documentations index at all - although descriptions are still present and
		  can be found by 'Search'

		  Another solution may be to manually add each member function using:
			.. currentmodule:: my_mod
			.. autofunction:: method1
			.. autofunction:: method2

		  Or just remove Methods: from the class docstring (so this is done in MNE documentation)

		. google docstrings do not define how to list multiple parameters and their types in Returns: section
		  To use the same syntax as for the args, set the following option for napoleon in conf.py:
			napoleon_custom_sections = [('Returns', 'params_style')]

* DONE Photic stimulation: the duration is determined based on the annotation.duration read by MNE;
  the real end is annotation with keyword 'off'.
  Checking if the duration is read properly:
	. in some files - yes 
	. in some files - duration is set to 0 everywhere (81be60fc-ed17-4f91-a265-c8a9f1770517, 
          ffff1021-f5ba-49a9-a588-1c4778fb38d3.edf)
	  Moreover, in the latter the last stim starts with 1.0 Hz but ends with 'Eyes closed'
	  end there is no 'Off' annotation
	. Also, in some files (fff0b7a0-85d6-4c7e-97be-8ae5b2d589c2) some photic intervals
	  are encoded as 'Eyes Open', '9.0 Hz', 'Eyes Closed', 'Off'. In this case the duration
	  is still calculated correctly (in this record)
	. Typically the stimulation spans a set of frequencies. There is an interval without stim
	  when after previous freq is off. This interval often equals the duration of the on interval.
	  Algorithmically a sequency of on and no-stim intervals should be regarded as a single 
	  stim interval, if off periods are short enough.
	. Sometimes photic interval length changes, but most of the time interval for each frequency and
	  silent interval between frequencies are the same. Typical interval is around 5 s
  CONCLUSION: a safer way is to look for the 'Off' annotation rather than using the duration field.

Srirupa's pipeline detals
-------------------------
* prep.fit() call (which does the PREP pipeline):
	1. removes line noise only if a list
		prep_params["line_freqs"]
	   is not empty. ONLY IN THIS CASE it does this:
		- removes the trend by high-passing at 1 Hz (HARDCODED)
		- notches the power lines
		- ADDS THE TREND BACK!
	   There is no way to change the HP frequency used by removeTrend() without changing the
	   source code of the fit() function
	2. does the re-referencing. As a by-product channels are classified in different
	   groups (i.e. "bad_before_interpolation", "interpolated_channels", "still_noisy_channels",
	   etc. - need to figure out what they all mean)

* ICA step is done after PREP step and in particular includes 1 Hz (hard coded) HP filtering
  IN PLACE (thus original HP filtering may be not needed). However for that default MNE filter
  (FIR filter) is used
  It also uses the following settings:
	- number of ICA components is equal to the number of good EEG channels
	- hard coded random generator seed (right in the middle of the code)
  Then among reconstructed ICs is find matches to:
	- 'EOGn' channels - those describe eye blinks
	- 'EKGn' channels - those describe ECG
  No other channels names are checked

* The next question is how to choose FS for a ROI. Suggested procedure:
	- signals from ROI sources converted to SNRs (z-scores)
	- linear projection of all n signals onto k signals covering most of the variation
	  is calculated using PCA
	- the same projection is applied to the set of weights used obtain source signals. This way
	  one gets k weight vectors corresponding to ROI
	- is it possible to recalculate weight vector into FS?
	  	w = Rm1 h/(h' Rm1 h)
	  Assume pre-whitening, then w = h/h^2 => h = w h^2. In any case, we can have FS up to a
	  scalar multiplier. The latter can likely be found by assuming dipoles of a unit strength
	  in each ROI voxel and calculating the sensor output. Also, may be we do not need the scaling
	  factor if ultimately all calculations are done for the Z-scores 

	- For the noise covariance to be used in beamformer calculations one can choose the one
	  produced by randomly oriented completely uncorrelated sources in each voxel of the source
	  space. The magnitude of sources is chosen so as to produce the same total sensor field:
	  P = b'b = trace(b'b) = trace(bb') = trace(R)

* Working with strongly degenerate matrices:
  Turns out that keeping dimensions larger than the rank often causes standard
  functions fail:
	- sample covariance is not pos def - need to use nearest PD function
	- noise cov based on white uncorrelated sources and calculated as const HH' also
	  is not pos def
	- noise cov projected onto R's range as P HH' P has rank different (larger)
	  than that of P
  All these is explaned by noise in should-be-zero EVs which sometimes ends up above
  tolerance, or some functions simply do not check tolerance.

  CONCLUSION: better explicitly work in full rank subspace matrices, and only go to
  full sensor space at the final step.

  IMPLEMENTED SOLUTION. Inversion of R and search for N such that (R-N)>0 is done in reduced
  (full rank) space. Then corresponding matrices are projected back into original space, and
  REPLACED WITH NEAREST PD matrices. This way effectively pseudo-inverses are being used, but
  formally all matrices are PD.

  NOTE: In this case R^-1 * R = R * R^-1 != I (in fact, it is far enough from I). This is because
  the result is a projector UU' != I. However, one can verify that always trace(R * R^-1) = rank(R).
  This is because trace(R * R^-1) = trace(UU') = trace(U'U) = U.shape[1] = rank(R)

* Flipping the source time course signs along the label surface in accordance with the
  orientation of the surface at each source (this is NOT related to choosing orientation
  of the reconstructed dipole - see CONCLUSION at the end).

  Important part of the  process is defining a flip vector.This vector is returned by
  MNE function label_sign_flip() (file mne.label.py). flip vector contains
  only 1s and -1s. The flip is -1 if current normal is more than 180 degr off the "main"
  normal of a label, which is calculated via SVD of all (lh and rh) vertices of a label.

  Actual construction of a single time course depending on the mode parameter is determined
  by this mapping (see https://github.com/mne-tools/mne-python/blob/maint/1.4/mne/source_estimate.py#L3240):
     _label_funcs = {
        "mean": lambda flip, data: np.mean(data, axis=0),              # flip vector not used at all
        "mean_flip": lambda flip, data: np.mean(flip * data, axis=0),
        "max": lambda flip, data: np.max(np.abs(data), axis=0),        # flip vector not used at all
        "pca_flip": _pca_flip,

  Example of explicitly getting the flip vector, and how using "mean_flip" instead of "mean" affects
  the result is here:
	https://mne.tools/stable/auto_examples/inverse/compute_mne_inverse_epochs_in_label.html#sphx-glr-auto-examples-inverse-compute-mne-inverse-epochs-in-label-py

  This is what is done for "pca_flip":
      def _pca_flip(flip, data):
        U, s, V = _safe_svd(data, full_matrices=False)
        # determine sign-flip
        sign = np.sign(np.dot(U[:, 0], flip))
        # use average power in label for scaling
        scale = np.linalg.norm(s) / np.sqrt(len(data))
        return sign * scale * V[0]
  So:
	- Distribution of the main component over the label is calculated (U[0])
	- This distribution is correlated with the flip vector 

	- if correlation is negative, the time course of the main PCA component
	  is flipped (returned is sign * V[0]). This flipping of a single time course
	  does not additionally enhance the signal, as in the "mean_flip" case. It
	  is only needed to "ensure the same sign in similar STCs" as MNE puts it.
          AM: yes, it may be useful for group averaging

	- The amplitude of the label time course is: scale * V[0]
	      scale = |s|/sqrt(nvoxels))
          Now, |V[ivoxel]|^2 = 1 (in time domain). The total power of all voxels (in time domain)
          is |s|^2 because all time courses Vi are uncorrelated. Then RMS voxel amp is
          |s|/sqrt(nvoxels) - which is assigned to the label time course amp.

	  NOTE that singular values Si from this SVD are related to eigenvalues of the
	  label time courses covariance Ei as
		Si^2 = (Ntime -1) Ei
	  - that is, there is additional coefficient ~ to number of time points (because
	  R = U E U' = (1/(Ntime -1) DD' = (1/(Ntime -1) U S^2 U', where D is the label data)
	  Also,
	  |s|^2 = tr(S^2) = (Ntime -1) tr(E) = (Ntime -1) tr(R)
	  Thus the same normalization via the eigenvalues of label covariance is
		scale = sqrt[(Ntime -1)tr(R)]/sqrt(nvoxels)
	  Now, scaled principle component returned by MNE is
		Pi = scale * V[i] = (1/Si) * scale * Si * V[i]
	  	Si * V[i] = Ui'* D
	  	Pi = (1/Si) * scale * Ui' * D = (1/Si) * scale * Ui' * W_label' * Dsensor
	  We have
		scale / Si = sqrt[(Ntime -1)tr(R)]/sqrt(nvoxels) / sqrt((Ntime -1) Ei)
			= sqrt[tr(R)]/sqrt(Ei * nvoxels)
	  So finally
	  	Pi = sqrt[tr(R)]/sqrt(Ei * nvoxels) * Ui' * W_label' * Dsensor
	  (VERIFIED by comparing with MNE extract_label_time_course() result)

  Q: This flipping idea assumes that inverse solution already oriented the dipoles in some
     non-random way. What exactly is assumed (i.e. how dipoles produced by inverse solution
     are originally oriented?)
  A: For min-norm family, this is determined when creating the inverse operator
     using function minimum_norm.make_inverse_operator(). Then the sign is simply
     that of a result of apply_inv(Minv * B) for a voxel. Minv is a vector solution, 
     possibly weighted towards normal to the surface. apply_inv() has pick_ori parameter
     which ultimately defines the orientation and the sign of the time course.

     What is done when extracting label time course is an ADDITIONAL FLIPPING for example
     to avoid signal cancellation within a label. That is - it IS NOT RELATED TO FORWARD SOLUTION,
     it is an ad-hoc trick. 
	- 'mean_flip' settings in extract_label_time_course() flip time courses which are
	   opposite to the "dominant" orientation of a label, just to get a larger signal.
	- for 'pca_flip' flipping does not enhance the signal, because only a returned time
	  course is flipped; it is only used to have "its sign consistent" - see explanation
	  above for _pca_flip() function.

  CONCLUSION: this additional flipping has nothing to do with setting proper orientation
  of the source dipole. It only makes sense for a label, and is a trick to enhance signal
  one constructing a single label time course. Once the global stc exists from any inverse
  solution, this approach can be applied (for both MNE and beam solutions).

* Power spectra calculations
  --------------------------
  Theory:
  Inputs: SR, frequency resolution df

  Number of point per segment in the Welch method n ('nperseg' parameter in welch()):
  As the freq range of the signal (neg + pos freqs) is [-SR/2, SR/2] with n total (neg + pos)
  frequencies, we have df = SR/n. Then we simply get
  n = SR/df

  In our case SR = 256 Hz so for 1 Hz resolution the scipy's default nperseg = 256 is OK for
  linear frequency scale. For log scale:
  Given fmin, fmax and total points nf (including end points):
  dlogf = (log(fmax) - log(fmin))/(nf - 1)

  The necessary linear df is defined by the lowest end of the spectrum, therefore
  df = 10^(log(fmin) + dlogf) - 10^log(fmin)

  After the linear PSD is found, value for each non-linear frequency is calculated as:
	- find the closest linear frequency
	- assign this frequency PSD which is an average over the interval from previous log frequency

* Choosing wavelet scale and length for CWT in scipy
  --------------------------------------------------
  For scipy morlet wavelet, the wavelet main exponent is
    E(n) = exp(j*w*n/s),
  where n is the sample number. Therefore to get to Hz:
  t = n/fs, then in real time units
    E(t) = exp(j*w*(fs/s)*t)
  Thus the central frequency of the wavelet at scale s is:
    fc = (w/2 pi)*fs/s
 
  NOTE that when w ~ 6 and s = 1 ("mother wavelet") fc ~ fs so the wavelet
  is UNDERSAMPLED. The mininal allowed scale is s = 2.

  For a given frequency f, the corresponding scale is chosen so that fc = f, thus
	s(f) = (w/2pi)*fs/f
 
  Choice of the number of points for wavelet depends on w. For 
  scale 1, w ~ 6 the wavelet != 0 for 6 consequtive points only and mainly
  shows 1 half-wave (due to undersampling). A good smooth plot is obtained for m = 100,
  s = 16 which corresponds to rel frequency 1/16.
  The scipy.signal.cwt calculates m as follows:
    m = min(10 * s, len(data)),	# and this works for w ~ 6, as shown below.
  One cannot change this expression in scipy.cwt.

  In general, the length "m" for N cycles at scale s is calculated as follows.
  fc = (w/2pi)fs/s;				# wavelet fc for scale s
  L = N T = N (1/fc) = N (s/fs)*(w/2pi)^-1	# Length in seconds

  m = fs * L = N s*(w/2pi)^-1			# Number of points given N, w, s

  !!! When w = 2pi, one gets N cycles in exactly N*s points !!!
  
  But in fact one can use m = 5 * s, because the Morlet wavelet only lasts
  5 cycles - and is zero beyond those.

  For a particular case of fs = 256, f = 1 Hz, w ~ 6 yields:
	s = 256
  	m = 10*s = 2560 for 10 cycles

 Comparing to PyCWT wavelets:
	Complex Morlet wavelet in pycwt:
	The expression is
	w(t) = (pi*B)^(-1/2) * exp(-t^2/B) * exp(2*pi*j*C*t)

	The scipy's morlet2 wavelet is
	w_sp(t) = pi^(-1/4) * exp(-t^2/2) * exp(j*w*t)

	Thus to compare with scipy.cwt one needs to set 'cmor'
	wavelet with B = 2, C = w/2pi, and also MULTIPLY THE
	CWT AMPLITUDE by B^(1/2)pi^(1/4)

* Fitting parameters to the PSD (linear freqs, using spectra from Welch step)
	- The model parameters min_peak_hight (default 0.1) and peak_threshold
	  (default 2.) in fact do not depend on the abs PSD values, because they
	  refer to log10 of PSD. Indeed, they both refer to the differences in
	  log power, which is a log of dimensionless ratio.

      *** They are always using log10 (not decibels) ***

	  This is clear for MIN_PEAK_HIGHT which is diff in log power between the
	  peak max and fitted aperiodic component. It is also ofthe referred to
      as "ABSOLUTE THRESHOLD" which is confusing.

      Tutorial says it's ok to set min_peak_height to 0 if there is no reasonable
      estimate available. However, for peak-less flat spectra this will result
      in overfitting and finding lots of false peaks.

	  However, this is also true for PEAK_THRESHOLD. In tutorials it is ofteh
      referred to as "RELATIVE THRESHOLD" and defines min number of STANDARD 
      DEVIATIONS of the flattened log10(P) any peak should have.

      In fact setting of the relative threshold to 2 (default) means that any peak
      is really large compared to typical fluctuaions in the flattened spectrum.

      NOTE: the ABSOLUTE value (in log10 units of flattened spectrum) of this
      peak threshold changes with each iteration (because the residual flattened
      spectrum goes down) and it is absolutely normal for this absolute value
      to go below the min_peak_height.

      The peak is kept only if it is above BOTH absolute and relative thresholds.

	  However both these parameters DO DEPEND on whether this is a POWER SPECTRAL
	  DENSITY or AMPLITUDE SPECTRAL DENSITY. For the latter the defaults should
	  likely be chosen 2 times smaller than the defaults (which are for PSDs).
	  In our case we use PSD (not amplitudes) therefore standards defaults apply.

	  The only parameter which does depend on the units and is not dimensionless,
	  is the APERIODIC OFFSET.

	- Typical peak heights for alpha, beta with default parms are ~0.4 - 0.6 
	  These do NOT depend much on setting of the peak threshold, but NUMBER
	  OF FOUND PEAKS DOES DEPEND ON SETTING THE PEAK THRESHOLD. Keeping it at
	  2 looks like a good idea.

	- OBSERVATION: the fitted model with a good R^2 (0.97) may not follow
	  the actual spectrum very well everywhere, especially when there are
	  double close peaks. However the peak frequencies are usually picked up
	  accurately.

	- OBSERVARION: min peak width 1 Hz often allows to pick up environmental
	  lines and those are assigned this width of 1 Hz. However making min width
	  3 Hz STILL PICKS THOSE LINES - but just assigns them broader widths.
	  Another effect of this is that close double peaks are simply replaced with a
	  single peak, and peak frequencies of all are affected.
	  CONCLUSION: MIN PEAK WIDTH is a very SENSITIVE parameter.

      Authors suggest that this parameter should be AT LEAST TWICE THE FREQUENCY
      RESOLUTION. (So 1 Hz in our case is the bare minimum)

	- OBSERVARTION: max peak width is less sensitive; usually this parameter does not
	  affect the widhts of well defined peaks found; however it affects the width
	  assigned to the broad peaks like beta. Increasing it to 12 Hz was OK and only
	  resulted in the latter change

==============================================================================
* General explanation about label scores
==============================================================================

  For the overall assessment, annotators assigned a score of 1 for a confident
  normal interpretation, 2 for a low-confidence normal interpretation, 3 for
  a low-confidence abnormal interpretation, or 4 for a confident abnormal interpretation.
  For each of the four abnormality categories, we applied a similar scale, where 1
  indicated a confident absence, 2 indicated a low-confidence absence, 3 indicated a
  low-confidence presence, and 4 indicated a confident presence of the specific finding.

How to select the number of factors:
    https://en.wikipedia.org/wiki/Parallel_analysis
(just one criterion)
    https://www.rdocumentation.org/packages/psych/versions/2.5.6/topics/fa.parallel
 
One way to explain why we want to select a small number of factors is Very Simple Structure:
    https://www.rdocumentation.org/packages/psych/versions/2.5.6/topics/VSS

FA can be combined with a “rotation”:
    https://www.rdocumentation.org/packages/psych/versions/2.5.6/topics/fa

My personal preference is “Varimax”.

When it comes to a specific factoring method, I prefer:
    **Principal Axis Factoring**.
fm="pa" will do the principal factor solution

Why I prefer FA with ‘Principal Axis Factoring’ in comparison to PCA:

A correlation matrix can be considered as a combination of common effects, individual effects, and noise.
FA’s Principal Axis decomposes only the common effects, while PCA decomposes the entire structure
(as I understand).

* Based on AI recommendatiions for detecting epi features from amp distribs
    - Calculate
        Relative band power (delta/theta/alpha/beta)
        Kurtosis peak frequency
        Heavy-tail index - kurtosis is OK 
        CAN'T: Inter-band correlation of extreme events (we can't)
        Inter-hemispheric divergence - auto by ROIs

    - Based on those, calc indicators: (ranked)
        Band-limited kurtosis increase (15–40 Hz) - kurt mean, std in this band
        Heavy-tailed amplitude distributions - done above
        Focal delta/theta power excess  - use delta/theta, theta/alpha, alpha/beta ratios
        CAN'T Cross-frequency transient bursts
        Spatial asymmetry of above features - auto (ROIs kept)

  Thus, EPI-TARGETED FEATURE SET IS:
    For each ROI:
        delta/theta, theta/alpha, alpha/beta power ratios (3 parms)
        kurt peak freq (1 parm)
        kurt mean, std in 15 - 40 Hz band (2 parms)

  Also, one wants to account for LH, RH differences. In Destreux (147 chans),
  all channels are paired except ['G_subcallosal-lh']. We want to transform
  all features from current ROIs to mean, diff over pairs; that is instead of
  ROI-lh, ROI-rh there will be ROI-avg = (ROI-lh + ROI rh)/2, ROI-dif = ROI-rh - ROI-lh

  NOTE: verified that stored are CWT amps, not powers.

* AI considerations regarding feature selection:
    1. Train XGBoost
    2. Remove bottom 60–80% by gain importance
    3. Apply null importance selection
    4. Final check with SHAP or permutation importance

  This often reduces:
    5000 features → 200–400 strong features (our case)

  However, pruning unimportant features will only improve
  classification, when:
    Many irrelevant/noisy features exist
    Sample size is small relative to feature count - NOT OUR CASE
    Features are highly correlated or redundant
    The model is sensitive to noise (e.g., linear models, k-NN)

  Otherwise the benefits are faster training and better generalization,
  but classification improvement may be negligible.

* Apr 13. SUMMARY OF OBSERVATIONS REGARDING BLANK FREQUENCY INTERVALS
  For randomly shuffled labels, we see:
    - The stat moments are now appearing in random order, with higher moments like skew
      and kurtosis getting importance (which was never the case for true labels)

    - We STILL OBSERVE BLANK FREQUENCY INTERVALS for low moments (mean, median) and a bit
      of that for STD - but not for high moments.

  Ironically, we get classification results better than we have for real labels for
  Focal Epi (AUC ~ 0.4) :)))

  For real Abnormality labels, we see:
    - The BLANK FREQUENCY BANDS ARE QUITE STABLE with respect to the random seed used

    - The widths of those bands gradually decrease when increasing the initial number of
      features used for consensus and may disappear completely (24k features) for the most
      important moments - then they appear in the higher moments

    - The higher stat moments start to appear among the important features when increasing
      the total number of features; they were never used for 6k or 12k features

    - Overall ACCURACY GROWS SLOWLY WITH THE NUMBER OF FEATURES USED, but the overall improvement
      is minimal: AUC is ~0.864 for 6k features, 0.878 fir 12k features, 0.884 for 24k features.

  So conclusions are that BLANK FREQUENCY INTERVALS ARE A REAL THING (not a bug), and that xgboost
  prunes unimportant features in this order: first the higher stat moments, then frequencies in
  bands 4 - 8 Hz and > 32Hz, then some ROIs (if the number of features goes very low).

  This order somehow reflects the way the features array is initially organized:
  ROI x frequency x (mean, median, std, skew, kurtosis). Then after flattening the array the most
  fast changing feature is the stat parameter, then the frequency, then ROI - exactly the order
  how the features are pruned. Совпадение? Не думаю... (С) :)
